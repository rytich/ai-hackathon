# Claude Code 活用ガイド記事の調査と AF への取り込み判断

## 目的

外部記事の知見のうち、AF（agentic-framework）に取り込むことで改善が見込めるものを特定し、優先度をつける。

## 情報ソースの性質（重要）

梶谷健人「この3連休でClaude Code活用力をワンランクアップしたい人のためのリーディングガイド」。
**リーディングガイド形式**で、17テーマの紹介文のみ無料、詳細は各メンバーシップ記事（¥1,980〜/月）。
したがって取得できたのは**論点レベル**であり、実装詳細は原典に含まれない。以下は論点を AF の文脈で再解釈したもので、記事の実装をそのまま写したものではない。

## わかったこと（記事の論点）

- AI を「仕事の OS」として組み込む段階への移行。テクニック数より仕組み構築。
- Codex と Claude Code の**両刀使い**。速度が要る軽量業務＝Codex、深い思考が要る重要案件＝Claude Code。
- 重要な仕事ほど答えが浅くなる。原因は指示テクニックでなく**文脈・背景の提供不足**。What/Why/How を含める。
- レビューは**ハイライト＋インラインコメント→AI が差分反映**が速い（記事は Notion 例、修正速度 3〜4 倍）。
- **非エンジニアに Git/GitHub 作法を求めるのは難易度過高**。レビュー導入＝ボトルネック、不導入＝カオスというジレンマ。
- セッション記憶はリセットされる前提で「勝手に学ぶ仕組み」を意図的に設計する。
- 対外成果物は HTML 出力の方が見やすく届けやすい。

## AF の現状とのギャップ

| 論点 | AF の現状 | ギャップ |
|---|---|---|
| エージェント使い分け | `codex-claude` profile で両方有効化できるが、AGENTS.md は「どちらで作業する場合も同じ規約」と書くのみ | **どちらをいつ使うかの基準が皆無**（実質同一視） |
| 企画成果物のレビュー | レビューは GitHub PR ベースのみ | 「企画と実作業を分離」と決めたのに、**企画（`docs/planning/`）の承認手段が未定義** |
| 指示の型 | Done の定義・real-use gate など**出力側**の規律は厚い | **入力（指示・Issue 記述）側の規律がほぼ無い** |
| 非エンジニア参加 | 1 Issue = 1 branch = 1 PR / worktree / gh CLI が前提 | `knowledge-base.md` の維持機構表は business/support/materials の主担当を非エンジニアと定義済み。**両立していない** |
| 学習の昇華 | work-notes / decisions に履歴は残る | そこから `.agents/skills/` へ**昇華させる経路が未定義** |
| 出力形式 | 全て markdown | 対外資料の届けやすさの指針が無い |

## 示唆（優先度）

- **P1（本 PR で対応）**: エージェントのタスクルーティング / インラインレビューの標準化 / 指示の型。いずれも既存構造に追記で乗り、既に codex-claude を導入済みのプロジェクトへ即効。
- **P2（別途）**: 非エンジニアの参加経路（AF の設計矛盾のため運用方針の決定が必要）/ 学習の昇華経路 / 出力形式。
- **見送り**: スキルマップ（人材評価は AF スコープ外）、UX メソッド・デザイン品質（AF は技術スタック非依存が原則）、Mac 自動化（端末固有）、仕事と私生活を 1 フォルダに同居（AF は repo 単位の設計のため衝突）。

## 未確認事項

- 記事の実装詳細はメンバーシップ限定のため未確認。上記は論点からの再構成であり、原典の具体手法と一致する保証はない。
- レビュー手段は記事が Notion 例なのに対し、AF では git 内で完結する crit を採用した（外部サービス依存を避けるため）。この判断は [../../decisions/2026-07-15-p1-agent-routing-review-instructions.md](../../decisions/2026-07-15-p1-agent-routing-review-instructions.md) に記録。
