# 判断: 生成物（outputs/）のコミット方針を AF 本体と導入先で分ける

## 日付
2026-07-15

## 背景 / 課題
P2-6（成果物の出力形式）の検証（[../planning/research/2026-07-15-output-format-verification.md](../planning/research/2026-07-15-output-format-verification.md)）で、対外資料を HTML で配布する価値は確認できたが、生成物を git にコミットするか否かの方針が未定だった。AF 本体・導入先とも `.gitignore` が存在せず、`outputs/` は untracked のまま放置されていた。

## 選択肢
- A: どこでも `outputs/` をコミットしない（生成物は再生成できるから不要）
- B: どこでも `outputs/` をコミットする
- C: AF 本体はコミットしない、導入先はコミットする（採用）

## 決定
C を採用。判断基準は**リポジトリの種類ではなく、その生成物に受け手がいるかどうか**。

- **AF 本体**: 生成物はフレームワーク開発の副産物（デモ用デッキ、検証用レンダリング）で配布先が存在せず、bootstrap で配られるものでもない。`outputs/*` を ignore し、方針を書いた `outputs/README.md` だけ追跡する。
- **導入先プロジェクト**: 対外資料・提案書・レポートは事業の成果物そのもので、非エンジニアが参照する最終形。`outputs/` をコミットし、受け手のいない `outputs/tmp/` だけ除外する。

## 理由
- AF の目的は「仕様、実装、レビュー、検証、引き継ぎを repository 内の成果物だけで再現する」こと。導入先で配布物が repo の外にあると、この原則が非開発カテゴリで破綻する。特に `knowledge/materials/` の主担当は非エンジニアであり、repo 外のストレージを前提にすると参照経路が失われる。
- 一方 AF 本体の生成物には受け手がいないため、同じ理屈が適用されない。A を全体に適用すると導入先で原則が壊れ、B を全体に適用すると AF の履歴が副産物で汚れる。
- あわせてバイナリの扱いを明文化した。git 履歴は追記型で、一度入れた pptx / pdf は消えない。テキスト形式（HTML / SVG / Markdown）は差分圧縮が効くためそのままコミットしてよいが、大きい・頻繁に更新するバイナリは Git LFS か外部ストレージ＋リンクに寄せる。

## 情報ソース
- P2-6 の実地検証: 原稿 5.5KB（md）から生成物 19.8KB（HTML）を作成し、4 レイヤー構造の表現力・共有性と、差分追跡性・二重管理リスクを比較
- 既存の `docs/knowledge/materials/README.md` が pptx について定めていた「原稿はここ、生成物は outputs/」パターン

## 影響範囲
- 新規: `.gitignore`、`outputs/README.md`、`templates/project/.gitignore`、`templates/project/outputs/README.md`、`docs/knowledge/materials/agentic-framework-overview.md`（原稿の実例）
- 編集: `docs/knowledge/materials/README.md` と配布テンプレート側のミラー（原稿と配布形態の分離、HTML の位置づけ、コミット方針への参照）

## 却下した案・再検討条件
- **A（どこでもコミットしない）**: 生成物は再生成可能という一般論は、コード の build artifact には当てはまるが、人間が読む配布物には当てはまらない。再生成にはエージェントと同じ道具立てが要り、byte 一致も保証されない。
- **B（どこでもコミットする）**: AF 本体の履歴が受け手のいない副産物で肥大する。
- **HTML を正本にする案**: 却下。差分が読めずレビューできないため、AF の「行単位で指摘を返す」レビュー原則と両立しない。原稿は markdown のまま。
- 再検討条件: 導入先でバイナリ配布物が肥大した場合は Git LFS の標準採用を検討する。`outputs/tmp/` の粒度が実運用で合わなければ見直す。
