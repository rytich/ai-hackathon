# 判断: 大きな差分は、エージェントが判断の要る箇所だけを事前アノテーションする

## 日付
2026-08-02

## 背景 / 課題

- AF は Inline Review を規約化していたが、**「いつ必須か」を定めるだけで「大きな差分をどう絞るか」は定めていなかった**。
- [PR #36](https://github.com/rytich/agentic-framework/pull/36)（25 ファイル / +1286）を crit でレビューしたところ、利用者から「差分が大きすぎて人間が毎回すべてチェックするのは難しい」という指摘が出た。
- 全部読む前提の運用は、実際には読まれないまま approve される。**レビューが通ったという記録だけが残り、実質は無審査になる。** これは規約があることでかえって危険な状態である。
- 一方でこの差分は、テスト 21 アサーション、実機 20 回連続実行、全 profile への awk 不変条件検査、リンク検査によって**機械的にはすでに検証済み**だった。人間が同じ箇所を読んでも機械より確かにはならない。

## 選択肢

1. **エージェントが判断の要る箇所にだけ事前コメントを打ち、人間はそれだけ見る。**
2. 差分を小さくする（1 PR あたりのファイル数に上限を設ける）。本質的だが、今回のように「規約・スクリプト・定義・配布物」が一体で意味を持つ変更は分割すると各 PR が単体で検証不能になる。
3. レビュー対象ファイルを機械的に絞る（変更行数の多い順に上位 N など）。実装は簡単だが、判断が要るかどうかと変更量は相関しない。今回最も重要だった箇所は 1 行の変更だった。

## 決定

- **選択肢 1 を採用する。** 人間に渡す前に、エージェントが判断の要る箇所にだけ行単位のコメントを打つ。
- コメントする基準を 5 つに限定する: 方針の選択が残っているもの / リスク許容度の判断 / 文面が実際に行動を縛るか / その環境では検証できなかったもの / 正しいが不自然に見えるコード。
- **機械的に検証済みのものにはコメントしない。** 代わりに検証コマンドと結果を PR / Issue に載せる。
- コメント本文には「何を判断してほしいか」を書く。選択肢があるなら列挙する。
- 応答の型を定める。resolve = 合意、返信 = 判断または追加検証の依頼、検証を依頼されたら意見ではなく実測を返す。
- crit 未導入のプロジェクトは PR のインラインコメントで同じことをする。**手段ではなく絞り込みの規律が本体。**

## 理由

- **レビューの目的は「人間が全部見たという記録」ではなく「機械が判定できないことを人間が判定すること」。** 機械が検証済みの箇所を人間に読ませるのは、レビュー予算を最も価値の低いところに使っている。
- 実際にこの規律を PR #36 に適用したところ、**25 ファイルが 7 箇所に減り**、そのうち 2 箇所（crabbox/symphony の検査方法、`eval` の是非）が本物の未決事項として浮かび上がった。残り 5 箇所は確認で済んだ。絞り込まなければこの 2 件は差分の中に埋もれていた。
- 変更量ではなく「判断が要るか」で絞る点が重要。**PR #36 で最も重要だった指摘は 1 行の変更**（`( set +o pipefail; eval "$check" )`）で、変更量で絞る方式では拾えなかった。
- エージェントが差分を作った当事者である点は利益相反ではなく、むしろ**どこで判断を保留したかを最もよく知っているのはエージェント**である。ただしそれゆえに「自分が自信のある箇所を隠す」危険があるため、基準を 5 つに明文化して恣意性を減らす。

## 情報ソース

- 実運用（2026-08-02）: PR #36 に対し `crit --pr 36` でレビューセッションを起動し、`crit comment <path>:<line>` で 7 箇所に事前コメントを投入。人間が 5 件を resolve、2 件に返信。うち 1 件は追加検証の依頼で、実測を返して判断材料とした
- crit 0.17.1（`crit --version`）
- 既存規約: [../framework/collaboration-rules.md](../framework/collaboration-rules.md) の Inline Review、[../framework/toolchain-flow.md](../framework/toolchain-flow.md)（人間レビュー面は crit に一本化）
- 契機となった Issue: https://github.com/rytich/agentic-framework/issues/33（crit を実プロジェクトで検証する）

## 影響範囲

- 更新: `docs/framework/collaboration-rules.md` の Inline Review に「大きな差分の扱い（エージェントによる事前アノテーション）」を追加
- `templates/project/` 配下への配布は不要。`collaboration-rules.md` は `bootstrap-project.sh` のコピー対象に既に含まれている
- Issue #33 の受け入れ条件「規約の過不足があれば `collaboration-rules.md` の Inline Review を更新した」に対応する

## 却下した案・再検討条件

- **差分を小さくする（1 PR あたりのファイル数上限）** — 却下。今回のように規約・スクリプト・定義・配布物が一体で意味を持つ変更は、分割すると各 PR が単体で検証不能になる。ただし分割できる変更を分割しない理由にはしない。再検討条件: 事前アノテーションを入れても人間が読み切れない規模の PR が常態化したとき。
- **変更行数などで機械的に絞る** — 却下。判断が要るかどうかと変更量は相関しない。PR #36 で最も重要だった指摘は 1 行の変更だった。
- **エージェントがコメントを打たず、人間が全部読む** — 却下。実際には読まれないまま approve され、レビューを通したという記録だけが残る。規約があることでかえって危険。
