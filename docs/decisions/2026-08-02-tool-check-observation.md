# 判断: 検査できない recommended 行は残し、無視されないかを観察する

## 日付
2026-08-02

## 背景 / 課題

- `check-agent-tools.sh` の検査定義のうち、`crabbox` は `scripts/cbx.sh` の存在、`symphony` は `WORKFLOW.md` の存在を見ているだけで、**ツール自体を検査していない**。
- どちらも多くのプロジェクトには存在しないファイルなので、**ほぼ常に「optional 欠落」と表示され続ける**。実際、AF 本体で `--profile codex-claude` を実行するとこの 2 件が毎回 optional として出る。
- 常に同じ欠落が出続けると、**出力そのものが読み飛ばされるようになる**。そうなると must の欠落も一緒に見落とされ、ゲートの意味が失われる。
- この点は PR #36 の全体レビューでも Minor として指摘され、crit の事前アノテーションでも未決事項として人間に判断を求めた。

## 選択肢

1. **このまま運用して観察する。**
2. 検査できない行は落とす。出力は静かになるが、`crabbox` / `symphony` が「AF が想定するツール」であることが機械可読な定義から消える。
3. 別の検査方法を用意する。`crabbox` は CLI の有無、`symphony` は常駐サービスの死活など。ただし両者とも導入形態がプロジェクトごとに異なり、汎用の検査方法が定まらない。

## 決定

- **選択肢 1 を採用する。** 現状の検査のまま運用し、出力が無視されるようになっていないかを観察する。
- 観察項目を明示する: **`crabbox` / `symphony` が常時 optional 欠落として表示され続けることで、`check-agent-tools.sh` の出力自体が読み飛ばされるようになっていないか。**
- 判断材料は「must の欠落を見落とした事例が出たか」。出たら選択肢 2 か 3 へ移る。

## 理由

- **どちらの副作用がより悪いかが、現時点のデータでは決まらない。** ノイズによる形骸化（選択肢 1 のリスク）と、想定ツールが定義から消えること（選択肢 2 のリスク）は種類が違う害であり、実運用を見ずに机上で比較しても答えが出ない。
- 選択肢 3 は汎用の検査方法が定まらない。`crabbox` は導入先ごとにラッパの置き場が違い、`symphony` は仕様であって特定の実装ではない（`toolchain-flow.md` の「実行の自動化層」参照）。無理に検査方法を決めると、今度は「検査が通らないのに導入されている」という別の誤判定を生む。
- **観察すると決めた以上、観察項目と再検討条件を書き残さないと観察されない。** 「様子を見る」は記録がなければ何もしないことと区別がつかない。
